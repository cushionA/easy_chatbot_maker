# sprint-plan — Sprint を作業指示書に分解する

このスキルは、本リポジトリのオーナー（駆け出し Web エンジニア、座布団さん）が AI とペアプロで進むための **作業指示書一式** を生成する。

## 入力

ユーザーから受け取る情報:

1. **Sprint 番号**（例: `Sprint 2`）
2. **Sprint ゴール**（自然文で OK）
3. **日数**（既定 3 日）

不足していたら必ず `AskUserQuestion` で確認する。Sprint ゴールが曖昧なら `design/README.md` の「次のステップ」セクションや `design/09_task_split.md` を読んで候補を提示する。

## 前提として読むファイル

実行開始時に必ず以下を確認する（既に読み込まれていなければ Read する）:

- `design/README.md` — 主要決定事項とドキュメント一覧
- `design/09_task_split.md` — [自分] / [AI] 委譲の判断基準（**正の判断基準**）
- `design/sprint1_plan.md` および `design/sprint1/day1.md`〜`day3.md` — フォーマットの参照実装
- 該当 Sprint の中心になる設計書（Sprint 2 なら `05_search_classification.md` 等）

これらが食い違ったら **`design/` を信じる**（CLAUDE.md の方針）。

## 委譲ルール（[自分] vs [AI]）

`design/09_task_split.md:6` の基準を機械的に適用する:

> 「面接で『これどうやって作った？』と聞かれて、その場で説明できる必要があるか」
> - YES → [自分]
> - NO → [AI]

該当タスクの典型:

| 種別 | 委譲先 |
|---|---|
| 設計判断 / インターフェース定義 / 認証ロジック / RLS ポリシー / プロンプト設計 | [自分] |
| 雛形生成 / 同パターン複製 / テスト一次実装 / migration SQL 量産 / UI コンポーネント | [AI] |
| 「最初の 1 個」 | [自分]（残りは [AI] で複製可能になる） |

判断に迷ったら **[自分] に倒す**。座布団さんが後で「これ説明できないな」となるのが最悪。

## 出力ファイル

### `design/sprintN_plan.md`（Sprint 全体マップ）

含めるセクション:

1. テーマ・期間・ゴール・完了時の状態
2. 全体マップテーブル（| 日 | テーマ | 詳細指示書へのリンク | 主成果物 |）
3. 各 day の概要（タスクリストのみ、詳細は day ファイルに譲る）
4. 進めるときの 1 サイクル（`09_task_split.md:107` のワークフローを再掲）
5. 「つまづいたらここを見る」表（症状 → 参照先）
6. Sprint 完了後に残るタスク

### `design/sprintN/dayX.md`（日次作業指示書）×日数

各 day ファイルの構成:

```
# Sprint N Day X 作業指示書（YYYY-MM-DD）

> テーマ: ...
> 完了時の状態: ...
> 推定所要: X〜Y 時間

## DayX-1. <タスク名> [自分] or [AI]

**目的**
何のために、面接で何を語れるか（1-2 段落）

**自分で書く理由** (←[自分] の場合のみ)
なぜ AI 委譲せず自分が書くか

**前提確認**
- [ ] チェック項目
- [ ] チェック項目

**手順**
1. ...（コマンドやコード片レベル）
2. ...

**完了確認**
- [ ] 検証コマンド or 動作確認
- [ ] テスト green

**詰まったら**
- 症状 → 対処

**AI 依頼テンプレ** (←[AI] の場合のみ)
\`\`\`
依頼文をそのままコピペできる形で
\`\`\`

---

(タスクを 3-6 個繰り返す)

## Day X 終了チェックリスト
- [ ] ...

## Day X+1 への引き継ぎメモ
- ...
```

## 分解の粒度ルール

- 1 タスク = 半日〜1 日で完了 = 1 PR の単位
- 1 日あたり 3〜6 タスク
- 最初の 1 タスクは前日からの「続き or 前提確認」にする（リハビリ）
- 各日に最低 1 つは [自分] のタスクを入れる（座布団さんの設計力を寝かせない）
- 同じテーマを複数タスクで分割するときは「最初の 1 個（[自分]）」→「残り複製（[AI]）」のパターンに寄せる

## 完了後にすること

1. `design/README.md` の「ドキュメント構成」表に新規 Sprint プランを追記
2. 生成した day1.md のパスをユーザーに伝え、「明日朝はこれを開いて Day1-1 から」と案内
3. **書き終わった作業指示書を git に commit しない**（ユーザーが内容を確認・修正してからコミットしたい）

## やってはいけないこと

- 設計書（`design/`）を勝手に書き換える — 食い違いを発見しても、まず指摘してユーザー判断を仰ぐ
- Sprint N の途中で別 Sprint の話を混ぜる（Kitchen Sink Session 防止）
- 「念のため」セクションを足して指示書を肥大化させる — 読まれない章を作らない
- [自分] タスクの手順を AI 委譲できる粒度に逃がす — 自分で書く部分は「インターフェース・型・SQL の骨子」までを必ず含める
