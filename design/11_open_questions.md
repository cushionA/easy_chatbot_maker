# 11. 未確定の運用判断・要検証項目

設計上は方針を決めたが、実装着手時 or 運用開始時に**実機で確かめる必要**がある項目。

## 採用面接デモ運用

### Q. BYOK の壁をどう超えるか

**現状の方針**：採用面接用デモテナントだけ、座布団さんの Google API キーを埋め込み。

**未確定の運用詳細**：

- 1日あたりの上限リクエスト数（Gemini Free Tier の制限を踏まえて）
- レート制限実装：誰のクエリで何回まで許可するか
- 採用担当には事前に「デモ用設定済みの URL」を渡す方式 or 共通デモテナント方式
- デモテナントのデータ汚染対策（採用担当が変なクエリ入れても挙動が崩れないか）

**実装後に決定**：実際の Gemini API 利用量を見て上限調整。

- 何分でデモするか（5分？10分？）

- 何を「触らせて」何を「見せるだけ」にするか

## インフラ選定の確認

### Q. Oracle Cloud Always Free アカウントが取れるか

- 日本クレカで弾かれる事例あり
- ARM A1 の空き枠は時期により枯渇
- 取れなければプランBへ

**着手前に試す**：未試行。最優先のアクションアイテム。

### Q. プランB の Supabase 自動停止対策

- 7日無操作で停止 → 復活は手動 or API ping
- GitHub Actions cron で週1ping、これで停止回避できるか実機検証必要

**実装後に検証**。

### Q. Render Free / HF Spaces の Embedding モデル安定性

- `multilingual-e5-base` は約500MB、Render Free の 512MB RAM で OOM 多発の報告あり
- HF Spaces CPU が代替候補だが、レスポンスタイムが許容範囲か未検証

**実装後に検証**。

## 検索チューニング

### Q. ハイブリッド検索の閾値

- `THRESHOLD_CONFIDENT`（top1 が即確定）
- `THRESHOLD_LOW`（LLM フォールバックへ）
- `α`（match_count 重み係数）

これらは実データで動かさないと適切値が分からない。**初期値で実装 → 実機チューニング**。

### Q. RRF の k パラメータ

- 標準は60、テナントごとにベストが違う可能性あり
- まず60固定で始める

### Q. 「キーワード完全一致」の判定基準

- exact match だけ？前方一致もOK？
- 問題名のみ？キーワード列も対象？

**初期実装**：問題名 exact match のみ高信頼ショートカット、それ以外はハイブリッドへ。

## マスタ運用

- 本格 Web 版でも Excel 継続？YAML / JSON も？
- スキーマバリデーション（必須カラム・型）の厳密さ

**初期実装**：Excel のみ対応、Phase 2 で YAML / JSON も追加。

### Q. マスタ更新時の差分処理

**初期実装**：全件上書き（シンプル）。差分は Phase 2。

## 設計の見直しが必要になりそうな箇所

### Q. マルチターン対話の文脈保持

既存 Streamlit 版は「直近3発言を結合」する単純実装。本格版で：

- ユーザーが連続して質問した時、どう文脈を引き継ぐか
- 「それの詳細を」のような代名詞参照に対応するか
- LLM Query Rewriting で前提を補強するか

**Phase 2 で本格対応**、MVP は既存ロジックそのまま。

### Q. ナレッジマスタが大きい時の挙動

- 1000問題超えた時の検索性能
- pgvector HNSW のパラメータ調整
- カテゴリ絞込が効かないクエリの挙動

**実機検証**。Free tier で1000問題テナントが現実的かは未検証。

### Q. 埋め込みウィジェットのスタイリング

- 利用者サイトの CSS との衝突
- Shadow DOM で本当に分離できるか
- レスポンシブ対応

**実装時に検証**。
