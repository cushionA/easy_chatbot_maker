# 11. 未確定の運用判断・要検証項目

設計上は方針を決めたが、実装着手時 or 運用開始時に**実データ / 実機で確かめる必要**がある項目。各項目を「**論点 / 選択肢 / 暫定方針**」で整理する。検知の式は [05_search_classification.md](05_search_classification.md)、収集の作法は [06_destinations.md](06_destinations.md)、データ戦略は [07_data_strategy.md](07_data_strategy.md)。

## 検知（F2）の較正

### Q1. 検知パラメータ（`ε / N_min / M_min / Z_TH / halflife / K`）の較正方法

- **論点**: 新出・急上昇・廃れの閾値を実データで動かさないと「ノイズ垂れ流し」か「何も検知しない」に振れる。
- **選択肢**:
  - (a) ラベル付き固定データセット（既知の過去トレンド: Rust 台頭・jQuery 衰退・各年の「次の MCP」等）で precision/recall を見て手調整。
  - (b) グリッドサーチ + 回帰テストで F1 スコア最大化。
  - (c) ベイズ最適化で多次元同時探索。
- **暫定方針**: (a) を基準。`design/sprintN` の検知回帰テスト（[13_testing_strategy.md](13_testing_strategy.md)）に固定データセットを用意し、初期値で実装 → precision/recall を見て手調整。パラメータは環境変数 or 設定テーブルで保持。較正ログを残す。

### Q2. 新出のクロスソース裏取り `N_min` の妥当値

- **論点**: `N_min` が小さいと一発ネタ / タイポを拾い、大きいと本物の新語を取りこぼす。
- **選択肢**: `N_min = 2`（緩い・JP 限定語も拾う）/ `3`（標準）/ `4+`（厳しい・確実だが遅い）。`M_min`（最小サポート）との組み合わせも論点。
- **暫定方針**: `N_min = 3` / `M_min = 5` で開始。locale 別に別値を許容（JP はソース数が少ないため `N_min` を下げる余地）。Q1 の較正で確定。

### Q3. 急上昇 z-score の低カウント域での安定化

- **論点**: 言及が少ない語は `share` の分散が大きく、z-score が暴れて偽陽性が出る。
- **選択肢**:
  - (a) `recent_mentions >= M_min` の足切りのみ。
  - (b) ベイズ平滑化（事前を足して低カウントを引き戻す）。
  - (c) Poisson surprise / 変化点検知（CUSUM・ベイズ）に切替。
- **暫定方針**: (a) + (b)。MVP は EWMA + z-score を基準にし、低カウント域はベイズ平滑化で安定化。surprise / 変化点は fast-follow の比較検証項目。

## 用語辞書・正規化（F9）

### Q4. 用語辞書の初期ブートストラップ（seed 辞書の作り方）

- **論点**: 起動時に辞書が空だと正規化が効かず、全部「新規候補」になってトレンドがゴミになる。
- **選択肢**:
  - (a) 既存の技術タグ集合を seed に流用（GitHub topics / Stack Exchange tags / Qiita tags / npm・PyPI パッケージ名）。
  - (b) 公開技術用語辞書 / Wikipedia カテゴリから抽出。
  - (c) 初回バッチの NER 候補を人手レビューして辞書化。
- **暫定方針**: (a) を一次 seed（タグは事実データで合法・既に正規化済みに近い）。別名（`k8s` ↔ `Kubernetes`）は手動 + タグの表記揺れから半自動生成。除外語リストは一般語辞書 + 運用中の dismiss フィードバックで育てる。

### Q5. 曖昧語の文脈判定の精度（`"Go"` = 言語か動詞か）

- **論点**: `is_ambiguous` 別名（`Go` / `Rust` / `Swift` 等）を共起語で判定するが、誤判定が出現数を汚染する。
- **選択肢**:
  - (a) 共起語ホワイトリスト（`Go` なら `goroutine` / `golang` / `module` 等が近傍にある時のみ採用）。
  - (b) ソース文脈（プログラミングタグの付いた記事内のみ採用）。
  - (c) Gemini に少数の文脈分類を投げる（コスト・レイテンシ増）。
- **暫定方針**: (a) + (b) を一次フィルタ、判定に迷うものだけ (c) に回す（コスト最小化）。曖昧語の判定精度は固定データセットでサンプリング測定し、閾値を調整。

## 近重複・dedup

### Q6. 近重複 dedup の embedding 閾値

- **論点**: クロスポスト（同一記事が HN / Qiita / dev.to に重複）を 1 件に寄せたいが、閾値が緩いと別記事を誤統合、厳しいと重複が残る。
- **選択肢**: cosine 類似度の閾値 `0.90` / `0.93` / `0.95`。`content_hash`（完全一致）で弾けない近重複のみ対象。
- **暫定方針**: `content_hash` で完全一致を先に除去 → 残りを embedding kNN で `>= 0.93` を近重複候補とし、初期は保守的（高め）に始めて誤統合を避ける。実データでクラスタの中身を目視して調整。

## BigQuery コスト

### Q7. BigQuery スキャン量の抑制

- **論点**: 無料枠（クエリ 1TB/月）を超えると従量課金。F1 / F2 / F5 が生ファクトを毎回舐めると即超過。
- **選択肢**:
  - (a) `occurrences` を `occurred_date` パーティション + `term_slug` クラスタリング。
  - (b) 事前集計 `daily_term_stats`（スケジュールクエリ）を読み元にし、ダッシュボードは生ファクト全件スキャン禁止。
  - (c) BI エンジン / マテリアライズドビューの利用。
- **暫定方針**: (a) + (b) を必須化。アドホックな全件スキャンを避け、スケジュールクエリのスキャン量も `INFORMATION_SCHEMA.JOBS` で監視。公開 DS（GitHub Archive）との結合は期間を厳しく絞る。

## 収集コンプライアンス（robots / ToS）

### Q8. 収集対象サイトの robots / ToS 個別確認の運用

- **論点**: 「合法ラインを引く判断」が題材の一級市民。対象追加のたびに robots / 利用規約を確認する運用を回す必要がある。
- **選択肢**:
  - (a) 新ソース追加時にチェックリスト（robots Disallow / Crawl-delay / ToS のスクレイピング条項 / API の有無）を必須化し `sources.robots_policy` に記録。
  - (b) robots は実行時に都度取得・解析して機械的に尊重（`FetchContext` 内蔵）。
  - (c) ToS は機械判定不能なので人手レビュー + 判断ログ。
- **暫定方針**: (a) + (b) + (c) を併用。**「需要 × 公式アクセスが無い × 合法」の 3 条件**を満たすソースのみ追加。規約禁止サイト（小説投稿サイト・pixiv・大手 SNS）は収集しない（[01_overview.md](01_overview.md) スコープ外）。判断ログを設計資産として残す。

### Q9. 派生データのみ保存の境界（スニペット長の上限）

- **論点**: 「短い文脈スニペット」は派生データだが、長すぎると本文の実質的複製になり、派生データの域を超えて合法性が揺らぐ。
- **選択肢**: 上限 140 / 200 / 280 字、または「用語前後 N トークン」。
- **暫定方針**: 用語を含む前後の短い窓（初期 ~200 字 / 1 文単位）に制限し、出典は必ずリンク。本文全文は抽出後破棄（[07_data_strategy.md](07_data_strategy.md)）。法務確認は本番運用前。

## 収集ヘルス（F8）

### Q10. `parser_broken` 検知の閾値とアラート運用

- **論点**: クロール対象のサイト構造変化を「取得件数 0 / 必須フィールド欠落」で捉えるが、正常な 0 件（その日トレンドが空）と区別が要る。
- **選択肢**: `consecutive_failures` 閾値（2 / 3 / 5）でアラート。過去の平均取得件数からの急落も併用。
- **暫定方針**: `consecutive_failures >= 3` + 「直近平均件数比で急落」を `parser_broken` 候補に。初期は緩めに通知し、誤報を見て閾値を上げる。クロールソースは API より監視を厚く。

## マルチテナント・セキュリティ

### Q11. プライベートソースの ES 分離（fast-follow / Phase 2）

- **論点**: テナント自社ブログ等を取り込む段階で、ES に RLS が無いためクエリ側でテナント分離を強制する必要がある。
- **選択肢**: (a) 単一共有インデックス + `tenant_id` フィルタ必須 / (b) index-per-tenant。
- **暫定方針**: (a)。グローバル文書（`tenant_id` なし）+ 自テナント文書のみ返すフィルタを**検索層のチョークポイント 1 関数**（`visibleDocsQuery`）に集約（[04_security_multitenant.md](04_security_multitenant.md)）。index-per-tenant は採らない。E2E でテナント越境が無いことを検証。

### Q12. RLS ポリシーの抜け漏れ検証

- **論点**: ポリシーバグはサイレント漏洩。テナント単位テーブル（`tenant_settings` / `watchlists` / `watchlist_items` / プライベート `sources`）の SELECT/INSERT/UPDATE/DELETE すべてに越境テストが要る。
- **選択肢**: 手動レビュー / E2E 自動テスト。
- **暫定方針**: testcontainers で本物の Postgres を立て `portfolio_app` で接続し、(1) テナント A から B のデータが全操作で見えない、(2) `SET LOCAL app.tenant_id` 未発行時に空集合（フェイルセーフ）、(3) グローバルデータは全テナントから読める、を E2E で常時検証（[04_security_multitenant.md](04_security_multitenant.md)）。

## インフラ・モデル運用

### Q13. Embedding 推論サービスの安定性

- **論点**: `multilingual-e5-base`（約 500MB）を Cloud Run / ECS（CPU）の RAM / コールドスタートで安定運用できるか、収集バッチの同時推論に耐えるか。
- **選択肢**: (a) 常駐最小インスタンス / (b) バッチ時のみ起動 / (c) ONNX 化 + Node 内蔵（`onnxruntime-node`）。
- **暫定方針**: MVP は実装速度優先で Python / FastAPI サイドカー（(a) or (b)）。レスポンスタイム・コールドスタートを実機検証し、ボトルネックなら Phase 2 で (c)（HTTP インターフェースは不変）。

### Q14. 無料枠 / 最小インスタンスのコールドスタート対策

- **論点**: フロント / API / 収集ワーカーを無料枠 / 最小ノードに載せた時のコールドスタート・スケール挙動。
- **選択肢**: 最小インスタンス常駐 / cron ウォームアップ / オンデマンド。
- **暫定方針**: 実機検証。面接デモ前のウォームアップは GitHub Actions cron をオプションで用意。

### Q15. LLM プロバイダの将来切替（BYOK）

- **論点**: F3 要約は Gemini（BYOK）一本だが、将来 Anthropic / Groq 等への切替や複数プロバイダ対応の余地。
- **選択肢**: Gemini 限定 / 抽象ラッパで複数対応。
- **暫定方針**: MVP は Gemini 限定。LLM 呼び出しは薄いラッパに隔離し将来切替可能に。出力は zod 検証で構造を固定。

## デモ運用

### Q16. 採用面接デモのデータ準備とシナリオ

- **論点**: 「いま立ち上がりつつある技術」を見せるには、ある程度の収集履歴（時系列）が要る。当日その場では作れない。
- **選択肢**: (a) 事前に数週間〜数ヶ月分を収集して `daily_term_stats` を貯める / (b) 公開 DS（GitHub Archive on BigQuery）から過去分を一括投入 / (c) 既知の過去トレンドの固定スナップショットを見せる。
- **暫定方針**: (b) で過去の時系列を BigQuery に投入してブートストラップ + (a) を並行。デモは F2（新出 / 急上昇 / 廃れ）→ F6 ドリルダウン（出典リンク）→ F3 要約の流れを軸に、5〜10 分で。

### Q17. F3 要約のシステムキー上限（デモ用）

- **論点**: デモテナントでシステムキー（座布団さんの Gemini キー）を使う場合、利用量と上限の管理が要る。
- **選択肢**: 日次リクエスト上限 / 要約はキャッシュ（`summaries`）優先で再生成を抑制 / デモ用テナント限定。
- **暫定方針**: グローバル `summaries` 生成は**システムキー限定 + per-tenant レート / 日次上限を MVP から実装**（「実利用量を見て調整」ではなく上限を先に置く＝金銭 DoS 防止）。`summaries` キャッシュを最大活用し新規生成を最小化。BYOK 生成は**テナント専用でキャッシュせずオンデマンド**。デモテナントのみシステムキー、一般テナントは BYOK。「BYOK 無ければシステムキーに暗黙フォールバック」はしない。

## 収集物の信頼境界（untrusted input）

### Q18. SSRF allowlist / prompt-injection 検査の強度

- **論点**: 「収集物 = 信頼できない入力」の防御（SSRF / プロンプトインジェクション / XSS / ReDoS）は設計の必須要件（[04_security_multitenant.md](04_security_multitenant.md)）。**やるかどうか**は確定、残る論点は**強度（誤遮断とのトレードオフ）**。
- **選択肢**: SSRF は (a) DNS 解決後 IP の拒否リスト / (b) 取得を専用 egress プロキシ経由に限定。プロンプトインジェクションは (a) デリミット + 指示固定のみ / (b) 出力ヒューリスティック検査も追加 / (c) 別 LLM で混入検知。
- **暫定方針**: SSRF は (a) を必須、本番は (b) egress プロキシも検討。F3 は (a)+(b)。プライベートソース URL 登録は admin 限定 + prefix 検証。検知漏れ / 誤遮断を運用ログで観測して閾値調整。

## ロードマップ・優先順位

実装着手の順序はまだ確定していない。候補:

1. インフラ雛形（Cloud SQL / RDS + OIDC + Secret Manager + OpenSearch + BigQuery、Docker / K8s）
2. プロジェクト雛形（Node API + React フロント + 収集ワーカー[BullMQ/Redis] + FastAPI Embedding）
3. DB マイグレーション（Postgres スキーマ + RLS + 2 ロール分離）
4. 認証・テナント解決（最小限）
5. **Source Adapter + FetchContext**（API ソース数本から、礼儀正しい取得の核）
6. 抽出・正規化（F9 seed 辞書）→ `occurrences` 投入 → `daily_term_stats`
7. **検知バッチ（F2）** + 回帰テスト
8. F1 可視化 / F6 ドリルダウン
9. F3 要約 / 関連トピック
10. クロールソース（GitHub Trending 等）+ F8 収集ヘルス
11. デプロイ・運用整備
