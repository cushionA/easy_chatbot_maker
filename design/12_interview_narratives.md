# 12. 面接訴求ポイント集

採用面接で「何ができるか」を語る際の引き出し。TrendScope の設計判断のうち**面接で評価される表現**を集める。語り口は一人称（`>` 引用ブロック）で示す。

## 全体ストーリー

> 「開発系 Web 上の"言及"を収集して、技術用語の **新出・急上昇・廃れ** を時系列で検知・可視化する、マルチテナント型のデータ収集 + 分析プロダクト TrendScope を設計した。スター数のような既存の集計値ではなく、Web 上の言及そのものを一次信号にして『いま何が立ち上がりつつあるか（次の MCP は何か）』を捉えるのが狙い。
>
> 技術スタックは入社先の実務標準に合わせて **TypeScript / Node.js**（React フロント + Node API + 収集ワーカー）に寄せ、ML 推論（Embedding）のみ Python に分離した。データは **Postgres（メタ）/ Elasticsearch（検索・エビデンス）/ BigQuery（時系列・検知）の 3 層**に配置し、Docker / Kubernetes でマルチクラウド可搬にしてある。
>
> 題材が他者サイトの収集なので、**合法ラインを引く判断**と**礼儀正しいクローラ**を設計の一級市民にした。UI の作り込みより、収集パイプライン・ML・データ基盤の堅さに価値を置いている。」

> 「この設計は実は、先に作っていた RAG チャットボット platform の**横断インフラ（RLS / OIDC / Secret Manager / ES / BigQuery / Docker・K8s / CI / テスト / BYOK / Adapter）をそのまま土台に流用し、ドメインだけクロール + トレンド検知へ載せ替えた**もの。マルチテナント型データプロダクトの土台は使い回せる設計にしてあった、という再利用性も語れる（[10_existing_streamlit.md](10_existing_streamlit.md)）。」

## 訴求ポイント別

### 1. API 主軸・クロール脇役という実務判断

> 「『収集』というと全部クロールで取りに行く印象を持たれがちだが、開発系の信号の大半は **API / フィードで合法かつ綺麗に取れる**（GitHub・Hacker News・Qiita・dev.to・Stack Exchange・npm/PyPI の DL 数、GitHub Archive は最初から BigQuery 上にある）。だから **公式アクセスがある対象は必ず API を使い、クロールは公式 API が無い隙間だけ**（GitHub Trending・記事本文・CHANGELOG）に限定した。
>
> クロールが脇役でも、そこは実務スキルの本体として手を抜かない。新ソースの追加は『需要 × 公式アクセスが無い × 合法』の 3 条件で判断する。**取りに行く前に取り方を選ぶ**のが実務の正解形だと考えている。」

ポイント: 「やった機能」より「**API を優先してクロールを最小化した判断**」を評価軸にする。

### 2. 合法ラインを引く判断力

> 「他者サイトを収集する以上、合法性は後付けではなく設計に内蔵すべき一級市民だと考えた。具体的には、**対象ごとに robots.txt と利用規約を読んで収集可否を決める**ところから始めた。
>
> 例えば題材として小説投稿サイトや Kaggle のデータも検討したが、**規約・robots を実際に調べた上で、スクレイピング禁止 / 再配布制約があるものは見送った**。需要があっても合法ラインを越えるなら収集しない、という線引きを `sources` テーブル（`robots_policy` / `rate_limit_rpm`）と設計方針の両方に落とした。
>
> 保存するのは **派生データ（用語頻度・メタ・短い文脈スニペット・embedding・要約）だけで、本文全文は持たない**。本文は抽出処理の最中だけメモリで扱い、用語抽出とスニペット生成が終わったら破棄する。出典は必ずリンクで返す（原文は相手サイトが source of truth）。根拠の一つは著作権法 30 条の 4（情報解析目的の利用）だが、**同条の但書・ToS（契約）・サーバ負荷は別軸で個別判断する**という線も合わせて語れるようにしておく（「30 条の 4 だから無条件で合法」とは断定しない）。順位・出現数・タグといった事実データ自体は著作権の保護対象外（[07_data_strategy.md](07_data_strategy.md)）。
>
> これは合法性・データ最小化・容量・削除要求対応を**同時に解決する**設計になっている。」

ポイント: 「**調べた上で見送った**」エピソードが、コンプラ判断力の証明になる。

### 3. 礼儀正しいクローラ + 収集ヘルス

> 「ソースごとに取得方法（REST API / フィード / HTML クロール）が違うので、`SourceAdapter` インターフェースで抽象化し、**HTTP の作法は `FetchContext` という共通チョークポイントに集約**した。robots 遵守・ホスト別レート制御（トークンバケット）・条件付き GET（ETag / If-Modified-Since で 304 活用）・429/5xx の指数バックオフ + ジッタ・連絡先入り User-Agent・静的は `fetch` で JS レンダリングが要る所だけ Playwright — これを Adapter ごとに書かせず 1 箇所に閉じ込めた（[06_destinations.md](06_destinations.md)）。
>
> 収集は**黙って腐るのが最悪**なので、収集ヘルス（F8）を設計の一部にした。取得件数 0 や必須フィールド欠落を `parser_broken` として検知し、『サイト構造が変わってセレクタが死んだ』を `sources.last_status` と連続失敗回数でアラートする。鮮度・失敗率もソース別に可視化する。**データが静かに古くなる事故を検知できる**のが運用上の肝。」

### 4. ML による検知（新出 / 急上昇 / 廃れ）

> 「トレンド検知の核は『新出 → 急上昇 → 定着 → 廃れ』のライフサイクルを 3 種のイベントで捉えること。すべて BigQuery の日次集計（`daily_term_stats`）を入力に算出する（[05_search_classification.md](05_search_classification.md)）。
>
> **新出（emerging）** は『昨日までほぼゼロ → 直近に複数ソースで出現』。新語は件数が少なくタイポ・一発ネタ・個人造語だらけなので、**クロスソース裏取り**を必須にした。1 つのブログが連発したのは数えず、`distinct_sources`（別々の媒体・著者）が閾値以上で初めて本物とみなす。これがノイズ除去の肝。
>
> **急上昇（rising）** は言及シェアの急増。投稿が多い日に全部が伸びて見えるのを防ぐため、まず **share = mentions ÷ 当日全用語 mentions で総量正規化**し、ベースラインの EWMA を平均、その標準偏差で **z-score** を取る。低カウント域はベイズ平滑化（事前を足す）で安定させ、最小サポート未満は足切りする。代替として Poisson surprise や変化点検知（CUSUM）も検討したが、MVP は EWMA + z-score を基準にした。
>
> **廃れ（declining）** は share が trailing peak の一定割合を一定期間連続で下回る、または回帰トレンドが有意に負。『jQuery 継続低下』のような衰退を出すとライフサイクルの物語が完成する。
>
> 用語の正規化（F9）が甘いとトレンドはゴミになる。別名マージ（k8s ↔ Kubernetes）・除外語（app/data 等の一般語）・曖昧性解消（"Go" は言語か動詞か）を辞書 + 共起文脈 + 必要時 LLM で行い、**誤検知レビュー（`detections` の dismiss）→ 除外語 / 別名へのフィードバックループ**で精度を上げる。」

ポイント: ノイズ除去の具体策（クロスソース裏取り・総量正規化・低カウント足切り・ベイズ平滑化）を言えると ML の解像度が伝わる。

### 5. 3 層データ基盤と BigQuery のコスト勘所

> 「データは役割で 3 層に分けた。**Postgres = エンティティ / 設定（編集の source of truth・RLS 対象）**、**Elasticsearch = 文書（エビデンス検索 BM25 + 関連トピック kNN）**、**BigQuery = 出現ファクト + 日次集計（トレンド・検知の素）**。検索は ES 主、時系列・検知は BigQuery 主、エンティティ編集は Postgres 主、と読み分ける（[03_db_schema.md](03_db_schema.md)）。
>
> トレンドの素は『用語 × 日 × ソース × ロケールの出現集計』という時系列ファクトで、これはメタ DB ではなく DWH に置くのが素直。しかも **GitHub Archive 等の公開データセットが最初から BigQuery 上にある**ので、自前の出現ファクトと同じ場所で結合・集計できる。
>
> DWH のコストはスキャン量で決まるので、そこが勘所。`occurrences` は **`occurred_date` でパーティション + `term_slug` でクラスタリング**し、期間・用語で絞ればスキャンが激減する。可視化・検知は生ファクトを毎回舐めず、**スケジュールクエリで日次更新する事前集計 `daily_term_stats` を読むだけ**にして、無料枠（クエリ 1TB/月）に収める。**収集頻度・BigQuery スキャン量・推論負荷のどれが先に課金に効くか**を予測できる状態で持っている（[07_data_strategy.md](07_data_strategy.md)）。」

### 6. マルチテナント RLS（軽量設計）

> 「トレンド本体（用語・出現・集計・公開ソース・文書）は全テナント共有のグローバルデータで、テナント分離の対象ではない。分離するのは **本当にテナント固有な情報だけ**（ウォッチリスト・テナント設定の BYOK キー参照・プライベートソース）。これを『**共有コーパス + テナントオーバーレイ**』と呼んでいて、本体データを無理にテナント複製せずコストと複雑度を抑える軽量マルチテナントにした（[04_security_multitenant.md](04_security_multitenant.md)）。
>
> 分離は Row Level Security 一択。schema-per-tenant は無料枠での運用が不可能で、RLS は Postgres 標準で運用シンプル。**DB 側で JWT クレームを直接参照するパターンは REST ゲートウェイ前提**で、Node API が Postgres に直接接続する構成では機能しない。そこで認可（JWT → `user_tenants` 照合）はアプリ層で完結させ、確定した `tenant_id` を **Node のデータ層がリクエスト / ジョブ単位トランザクションの先頭で `SET LOCAL app.tenant_id`** してから RLS が参照する設計に倒した。
>
> さらに **スキーマ所有者ロールは暗黙の `BYPASSRLS` を持つ罠**があるので、マイグレーション / グローバルデータ書込用の `portfolio_owner` とアプリ接続用の `portfolio_app`（`NOBYPASSRLS`）を分離し、テナント単位テーブルには `FORCE ROW LEVEL SECURITY` を付けた。ポリシーは `current_setting('app.tenant_id', true)` の missing_ok を使い、**セッション変数が未設定なら例外でなく空集合になるフェイルセーフ**にしている。BYOK の LLM キーは平文で DB に置かず Secret Manager に保管し、DB には参照（リソース名）だけを持つ二段防御。」

### 7. テスト（RLS 越境 E2E + 検知回帰）

> 「求人の必須要件が『Web アプリ開発のコーディングからテストまで』だったので、テストを後付けでなく設計の一部にした。
>
> 特に **RLS のポリシーバグはサイレント漏洩**になるので、E2E で明示確認する。テナント A / B を作り、A でログインして B のウォッチリスト・設定が SELECT/INSERT/UPDATE/DELETE のどれでも見えないこと、`SET LOCAL` 未発行時にテナント単位テーブルが空に見えること（フェイルセーフ）、グローバルデータは全テナントから読めることを自動検証する。実装は testcontainers で本物の Postgres を立て、`portfolio_app`（NOBYPASSRLS）で接続して検証する。
>
> もう一つの軸が **検知ロジックの回帰テスト**。新出 / 急上昇 / 廃れのパラメータ（裏取り数・z 閾値・halflife 等）を固定データセットで較正し、ロジック変更でトレンド判定がブレないことを担保する。主要フロー（サインイン → トレンド閲覧 → ドリルダウン → ウォッチリスト）は Playwright で E2E、単体・結合は Vitest、CI は GitHub Actions。**テストケースの定義は自分が握る**（特に RLS 越境ケースは漏洩したらアウトなので網羅を自分で詰める）。」

## 採用企業別の刺さりポイント

### データ収集・検索基盤・AI 系

- API 主軸・クロール脇役の取得設計 + 礼儀正しいクローラ（robots / レート / 条件付き GET）（**収集の実務感**）
- 合法ラインを引く判断（規約・robots を読んで収集可否を決める・派生データのみ保存）（**コンプラ判断力**）
- ML 検知（新出のクロスソース裏取り・急上昇の総量正規化 + z-score・廃れ）（**ML 技術選定**）
- 3 層データ基盤（Postgres / ES / BigQuery）+ BigQuery のコスト勘所（**データ基盤設計 + コスト感覚**）
- 収集ヘルス（`parser_broken` 検知）の可観測性（**運用設計**）
- RLS 越境の E2E 検証 + 検知回帰テスト + CI（**品質・テスト設計**）

### 汎用 Web / SaaS

- 軽量マルチテナント（共有コーパス + テナントオーバーレイ・RLS・FORCE・フェイルセーフ）（**SaaS 設計**）
- TypeScript / Node.js フルスタック + 型をフロント〜ワーカーで共有（**実装力**）
- Source Adapter パターン + DI（HTTP 作法を FetchContext に集約）（**抽象化能力**）
- 無料枠中心の運用 + スケール時の課金ポイント整理（**コスト感覚**）
- 旧チャットボット platform の横断インフラを土台に再利用した再ピボット（**設計の再利用性**）

## NG な語り方（避ける）

- 「Claude に全部書かせた」→ AI 任せに聞こえる
- 「とりあえずクロールした」→ 合法判断・取得設計がないように聞こえる
- 「最新技術を使った」→ 技術選定の理由がない

代わりに：
- 「**判断した**」「**選定理由は**」「**却下した代案は**」
- 「**○○のリスク（漏洩 / 違法収集 / コスト）を××で対応した**」
- 「**API を優先しクロールは隙間だけに限定した**」「**派生データのみ保存にした**」

## チート集：頻出質問と回答テンプレ

### 「なぜこの技術スタック？」

> 「対象プロダクト領域（自社 Web アプリ）の実務スタックに合わせ、フロント・API・収集ワーカー・テストを **TypeScript / Node.js のフルスタック**に寄せた。フロント〜バック〜ワーカーで型（ソース定義・抽出結果・検知結果のスキーマ）を共有でき、I/O バウンドな収集（多数の HTTP 取得を並行）とも相性が良い。検索は専用エンジン Elasticsearch、時系列・検知は BigQuery、メタは Postgres + RLS と役割で分けた。ML 推論（Embedding）のみ Python の独立サービスに分離し、将来は ONNX で Node 内蔵化して TS 一本化もできる設計にした。」

### 「収集はどうやってる？合法性は？」

> 「**API 主軸・クロール脇役**。公式アクセスがある対象は必ず API / フィードを使い、クロールは公式 API が無い隙間（GitHub Trending・記事本文・CHANGELOG）だけ。対象ごとに robots と利用規約を読んで収集可否を決め、禁止されているものは需要があっても見送る。保存するのは**派生データ（用語頻度・メタ・短いスニペット・embedding・要約）だけ**で、本文全文は抽出後に破棄し出典はリンクで返す。robots 遵守・レート制御・条件付き GET・指数バックオフは `FetchContext` という共通チョークポイントに集約してある。」

### 「トレンド検知はどうやってる？ノイズは？」

> 「BigQuery の日次集計を入力に、新出 / 急上昇 / 廃れの 3 イベントを算出する。ノイズ対策が肝で、**新出はクロスソース裏取り**（別々の媒体で複数ソース出現）+ 最小サポートで足切り、**急上昇は総量正規化した share の z-score**（投稿が多い日に全部伸びて見えるのを防ぐ）+ 低カウント除外 + ベイズ平滑化で安定化する。誤検知は人手レビューで dismiss し、原因が一般語なら除外語、表記揺れなら別名辞書へ反映して次回精度を上げるフィードバックループにしている。」

### 「マルチテナントどう作ってる？」

> 「**軽量マルチテナント**。トレンド本体は全テナント共有のグローバルデータにして分離せず、テナント固有の情報（ウォッチリスト・BYOK 設定・プライベートソース）だけを RLS で分離する。schema-per-tenant は無料枠で運用不可、RLS は Postgres 標準で運用シンプル。OIDC の JWT を Node 側で検証してテナントを解決し、データ層がトランザクション先頭で `SET LOCAL app.tenant_id` を発行、RLS がそれを参照する。`portfolio_owner` / `portfolio_app`（NOBYPASSRLS）のロール分離 + `FORCE RLS` + 未設定時フェイルセーフ。E2E でテナント越境がないことを担保。」

### 「インフラのコスト感は？」

> 「無料枠中心で運用し、スケール時の段階的有料化ポイントを整理してある。専用検索エンジン・DWH・収集ワーカーを持つので純粋な $0 ではないが、各要素に無料枠 / ローカル開発パスを用意した。特に **BigQuery はスキャン量が支配的**なので、日付パーティション + 事前集計テーブルでスキャンを抑える。**収集頻度・BigQuery スキャン量・推論負荷のどれが先に課金に効くか**を予測できる設計にしている。」

### 「テストどうしてる？」

> 「ユニットは AI に書かせることもあるが、**テストケースの定義は自分が握る**。特に **RLS のテナント越境がないことの E2E 検証**（漏洩したらアウト）と、**検知ロジックの回帰テスト**（固定データセットで判定がブレないこと）は自分でケースを網羅する。E2E は Playwright、RLS は testcontainers で本物の Postgres を立てて検証、CI は GitHub Actions。」
