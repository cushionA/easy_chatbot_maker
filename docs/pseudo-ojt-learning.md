# はじめに

AI を使うようになってから、**逆に新しい知識が身につかなくなった**。
最近、本気でそう思っています。
エラーが出たら原因を聞く。
分からない実装は書いてもらう。
設計に迷ったら丸ごと相談する。
たしかに開発は速くなりました。
でも後から振り返ると「自分は今日何を理解したんだっけ？」となる。
動くものはできているのに、自分の中には何も残っていない。

写経で身につかないのは昔から言われていましたが、AI への丸投げはそれよりタチが悪い。
写経は少なくとも手は動かしている。
丸投げは、その手すら動かさなくなる。
とはいえ、いまさらあの速度を捨てて AI なしの開発に戻る気はありません。

そこで考えたのがこれです。

⇒ **AI を「OJT の先輩」にする**

新人が現場で、雑用をこなしながら本物の仕事を覚えていく。
あの OJT を AI で再現する、というのが今回の話です。
退屈な作業や時間のかかるところは先輩（AI）が引き受けてくれて、自分は**"おいしい経験"だけ持っていく**。
速度を捨てずに、ちゃんと身につく。
そういう学び方を、実際に SaaS を 1 本作りながら回しています。

# なぜ「身につかなくなる」のか

そもそも、なぜ AI を使うと学べなくなるのか。
理由はシンプルで、**手を動かす量が減るから**です。
人は、自分で書いて・詰まって・調べて、ようやく覚えます。
この「詰まって調べる」を AI が全部肩代わりしてくれる。
ありがたいんですが、ここを飛ばすと記憶に残らない。

しかも厄介なのが、丸投げは**気持ちよく進む**ことです。
エラーは即解決、実装は一瞬。
進捗だけ見ると最高なので、学べていないことに気づきにくい。
気づいたら「動かせるけど説明できないコード」だけが増えていく。

OJT がうまくいくのは、この逆だからです。
雑用は振られるけど、判断する場面は自分でやらされる。
だから現場の知識が身につく。
これを AI との開発に持ち込めばいい、というのが発想の出発点でした。

# やり方①：おいしいところは自分、雑用は先輩に振る

OJT の肝は、**何を自分でやって何を任せるかの線引き**です。
ここを基準 1 つで機械的に決めています。

> **「これどうやって作った？ と聞かれて、その場で説明できる必要があるか」**

YES なら自分で書く。NO なら AI に振る。
迷ったら自分で書く側に倒します。後で「説明できないな」となるのが一番もったいないので。

題材にしているマルチテナント RAG チャットボットの SaaS で言うと、こう分かれます。

**自分でやる（＝おいしい経験）**
* テナント分離をどう守るか（RLS の方針、JWT クレーム設計）
* ハイブリッド検索のランキング設計（BM25 とベクトルをどう混ぜるか）
* 起票先を抽象化する Adapter のインターフェース定義
* LLM に渡すプロンプトの設計

**先輩（AI）に振る（＝雑用・時間泥棒）**
* マイグレーション SQL や EF Core のエンティティクラスの量産
* CRUD フォームや CSS などの定型 UI
* 同じパターンのコードの複製
* CI の YAML や Dockerfile などの設定ファイル

設計判断や肝になるロジックは、面接でも実務でも語れる「おいしい経験」です。
ここに時間を使う。
一方、ボイラープレートや手数の多い作業は、覚えても語れないし時間だけ食う。
ここは迷わず先輩に投げる。
こうすると**学びたいところにだけ手を動かす時間を集中できる**ので、速度を保ったまま覚えるべきところは覚えられます。

# やり方②：コードは自分で書いて、先輩には質問だけする

自分でやると決めたところは、**AI に書かせず質問だけします。**
「書いて」ではなく「どう書くべき？」と聞く。

* 「この処理、どういう方針で書くのがいい？」
* 「ここでこう書いたんだけど、何か見落としてる？」
* 「この設計、選択肢それぞれの欠点は？」

答えのコードをもらうのではなく、考え方をもらう。
最終的にキーボードを叩くのは自分なので、手が動いてちゃんと残ります。
これがまさに OJT で、先輩は隣で口は出すけど手は動かさない、という関係です。
VSCode の拡張機能（Copilot や Claude 系のもの）を開きっぱなしにして、書きながら聞く、を繰り返すだけ。

# やり方③：「最初の1個」だけ自分で書く

設計判断と単純作業の中間にあるものには、もう一工夫します。
**型を 1 個だけ自分で作って、残りは AI に複製させる。**

たとえば起票先の Adapter は、Redmine 版の 1 個目を自分で書いて構造を理解する。
2 個目の GitHub Issues 版は「これと同じ要領で」と AI に任せる。
Blazor のコンポーネントも、チャット画面 1 枚を自分で書いて、他のページは複製を頼む。
RLS ポリシーも、1 テーブル分を自分で書いてしまえば、残りのテーブルは AI が増分で書ける。
一度自分の手で型を通しているので、量産を任せても理解は残ります。
これも OJT 的で、最初の 1 件を先輩と一緒にやって、あとは任される、というあの流れです。

# やり方④：1手順ずつ進める

AI は頼めば 5 歩分まとめて書いてくれます。
でもそれをやると、どこで分からなくなったのかが分からなくなる。
なので 1 手順動かすごとに、これで合ってる？ なんでこう書くんだっけ？ と一度立ち止まる。
遅くなりそうに見えて、後戻りが減るので結局そんなに変わりません。
むしろ「分かったつもりで進んで後で崩れる」のが一番遅い。

# やってみてどうだったか

このやり方に変えてから、感覚がはっきり変わりました。

* **手が動くので、ちゃんと覚えている** — RLS もハイブリッド検索も、なぜその設計にしたかを説明できる
* **でも遅くない** — 雑用は全部先輩に振っているので、丸投げ時代とそこまで速度は変わらない
* **詰まらない** — 分からなければその場で聞けるので、独学みたいに止まらない

「速いけど身につかない」と「身につくけど遅い」の、ちょうど間に着地できた感覚です。

# おわりに

AI を使うと学べなくなる、というのは半分本当で半分は使い方の問題でした。
全部やってもらうから残らないだけで、**AI を OJT の先輩にする**と話が変わります。
退屈な雑用は先輩に振って、おいしい経験は自分で取りにいく。
やることは、説明できる必要があるところは自分で書く、それ以外は AI に振る、「書いて」ではなく「どう書く？」と聞く。
これくらいです。
AI を使い始めてから手応えがなくなった、と感じている人に、同じ悩みの抜け道として届けば嬉しいです。
